# Runner environment pitfalls

Keywords: session, focus, background, minimized, seed, random, research, wildlife, modpack, mod list, ModsConfig, savedatafolder, map size.

| Symptom | Action and limit | Where to inspect |
| --- | --- | --- |
| Batch stalls when unfocused | Launcher-owned processes reassert run-in-background without changing Prefs. Minimized map generation can still stall; restore the window. | `Harness/RunnerSession.cs`; [game facts](../game-facts.md#unfocused-and-minimized-windows) |
| Later command uses an old build | Close the session, rebuild/deploy deliberately, launch again. Production, adapter, harness and runtime hashes must match. Each batch gets a new colony even when the process is reused. | `rimtest.py`, `Harness/RunnerSession.cs` |
| Same seed gives different simulation | Creation is seeded; later simulation is not guaranteed repeatable. Never keep a Rand state pushed across frames. | [game facts](../game-facts.md#random-state) |
| Research disappears | Shared `Kit.Research` registers granted research for re-completion. Disclose it, and use it only when research completion is setup rather than the behavior measured. | `Harness/Kit.cs`, `Harness/Runner.cs` |
| Wild animals or incidents disrupt a case | Runner colonies suppress incidental simulation and remove wild quickstart animals. Spawn a required animal explicitly; this cannot prove natural incident/spawn behavior. | `Harness/Startup.cs`, `Harness/Runner.cs` |
| Requested map dimensions differ | Read actual dimensions, disclose mismatch, size layout searches accordingly. | Shared `PrepareMap`, `Kit.Area` |
| Work priorities reset; away-map ticks stop; stats drift | Verify the prerequisite itself and report unavailable environment or setup failure. Fix the prerequisite in the case's own setup rather than globally disabling another mod. | Run the case under a smaller mod set to confirm |
| Launcher exits during startup; game relaunches with `-WaitForExitingPid` | A mod restarted the game while loading. Load Them Last (`ferny.loadthemlast`) does this when its target mods are not last; it rewrites ModsConfig. In a mod set the rewrite only reaches the runner's copy; the launcher reports the relaunch. Kill the untracked replacement, put its target mods last in the set, and rerun. | Player-prev.log `[Restart]` lines. Runtime-observed 2026-11-08, RimWorld 1.7.5000 |
| Slow startup from the full modpack; ModsConfig left swapped after a crash | Runs use a mod set in `devtests.json` and `-savedatafolder=work/userdata/<argPrefix>`; the player's ModsConfig is never written. Use `--mods full` only for compatibility runs. 1.7 ignores Unity's `-logFile`; `Player.log` stays in the player's `Logs` folder. | [Mod sets](../authoring.md#mod-sets); `rimtest.py` `prepare_userdata`. Runtime-observed 2026-11-09, RimWorld 1.7.5000: a 3-mod set started in 17 s including launch; switching sets relaunched the session. `--mods full` validated offline only (about 1,500 mods). |
| Launcher crashes copying the developer DLL; `report runtime manifest does not match preflight` with the empty-string hash `e3b0c442...` | The mod loads its DLL from a load folder (`v1.6/Assemblies`). The launcher now installs developer DLLs next to `productionDll` (`Config.dev_assemblies`), and `RuntimeManifest.Root` uses the running mod's `RootDir` instead of the DLL's grandparent folder. | `rimtest.py` `load_config`, `Harness/RuntimeManifest.cs`. Runtime-observed 2026-11-09, RimWorld 1.7.5000: the crash and isolation failure were fixed, and a load-folder mod and a plain mod both passed afterwards. |
| `installed mod differs from the working tree` for every file of a mod installed from a built package; a batch passes or fails under another batch's mod settings | Set `"runtimeRoot"` to the package folder. Mod settings are process-wide: `run-all` now refuses sets that carry `DevTests/modsettings/<set>`, so run such batches one at a time. | `rimtest.py` `load_config`, `select_mods`. Runtime-observed 2026-11-09, RimWorld 1.7.5000: a run-all ran one batch under another set's settings; the batches passed when run separately. |
| Need another mod's Harmony patch already in place when the mod under test starts (conflict or compatibility gate) | Put a public `Mod` subclass in the developer DLL; Mod constructors run before `[StaticConstructorOnStartup]`, so its patches precede startup registration. Gate it per mod set with a marker file `DevTests/modsettings/<set>/Mod_<folder>_<Class>.xml`, which the launcher copies for that set only and clears on the next launch. Record whether the mod under test already owned each method when the probe ran and assert it did not, or a late probe passes for the wrong reason. Keep the probe's Harmony ID and namespace free of words the mod's own detection matches. Limit: it cannot precede patches the mod applies in its own `Mod` constructor (order between Mod classes is not guaranteed). | A probe `Mod` in the developer DLL. Runtime-observed 2026-11-12, RimWorld 1.7: the batch passed with the fix and failed without it. |
| `STARTUP FAILED` soon after launch | The runner could not start in the game: a game method it patches is missing, or two mods' developer DLLs are loaded. The message names the cause and `Player.log` in the run folder has the stack. With no message before `--startup-timeout`, the game never reached the main menu or `argPrefix`/`evidenceFolder` differ from the settings class. | `Harness/Startup.cs`, `rimtest.py` `check_startup`. Built 2026-11-12, not yet observed in game. |
| Run ends `INTERRUPTED` with exit code 2 and a full report | The launcher's `--timeout` was reached. The game closed the run 15 seconds earlier, so finished cases are reported; raise `--timeout` for long or multi-batch runs. A game that cannot respond is still killed, and `latest` then reports the run as having no report until the next run recovers it. | `Harness/Runner.cs` `Controller.Frame`, `rimtest.py` `game_deadline`. Runtime-observed 2026-11-12, RimWorld 1.7, through `self-check`: a stalled batch closed as interrupted with a report, and a killed one was recovered by the next run. |
| Developer DLLs left in the mod folder after a stopped launcher | They load in the player's own game but patch nothing without a launcher argument or the `install-dev` marker; the log has one warning line. The next run or `remove-dev` deletes them. | `Harness/Startup.cs` `Initialize`. Built 2026-11-12, not yet observed in game. |
| Startup fails after diagnostics | Intentional runner errors use their own marker, so the startup check doesn't mistake them for mod errors. Keep that separation in new diagnostics. | `Harness/DiagnosticBatches.cs`, `StartupLog` |

The focus/minimize behavior was observed in game on 2026-11-07, RimWorld 1.7.5000. The shared runner was verified with Core, Harmony and one mod only; a passing small set is not proof that it works on a large modpack.

Project instructions control run counts, deployment and mod-list changes. Preserve user saves, restore temporary configuration, close the owned session and check developer DLL cleanup. Full modpack compatibility remains separate from isolated-mod results.
